# 服务器硬件日志初判流程

目标：**用日志把"硬件到底哪里不行、要不要换件、换之前还要做什么"说清楚**，而不是复述日志。
结论必须能追溯到原始行（文件名 + 行号 + 原文）。

## 一、先固化输入，再动手

1. 明确日志来源：带外（BMC）还是系统侧（OS）。**两者都有才算证据齐全**：
   - 带外负责"硬件事实"（部件谁坏了、断电、风扇、电源、温度、掉盘）；
   - 系统侧负责"业务影响"（MCE/EDAC/AER/I/O 错误、重启记录）。
2. 缺哪一半就补采（见 `bmc-log-collection` 技能 / 工具 `hwlog_collect`），不要凭一半日志下硬件结论。
3. 时间对齐：带外时间戳是 BMC 时钟（常年不校时，可能偏几分钟到几小时），与 OS 时间对齐前不要下"因果关系"结论。
   对齐技巧：找同一次重启/断电事件在两个来源里的时间差，作为偏移量，再统一平移。

## 二、标准四步

### 第 1 步：识别与台账（不猜品牌）
调用 `hwlog_analyze`（或 CLI `dsh-hwlog analyze <路径>`）先拿到：
- 品牌识别结果 + 依据（DELL / HPE / Lenovo / 浪潮 / 华为 / 超微 / 曙光 / 中兴 / H3C / 富士通 / 通用）；
- 日志类型（IPMI SEL / iDRAC Lifecycle / IML / Redfish JSON / syslog / dmesg / 存储工具输出）；
- 设备台账：机型、序列号、BMC/BIOS 版本、CPU、内存总量、管理地址。

**台账为空 = 采集不完整**（缺 `getsysinfo`/`fru`/`dmidecode`），先补采再判。

### 第 2 步：分级（先看紧急，再看数量）
| 等级 | 典型事实 | 处置时限 |
| --- | --- | --- |
| 紧急 critical | 内存 UCE、CPU MCE/IERR、电源失效（单电源机型）/冗余丢失后再次掉电、风扇失效、过温/热保护、RAID 降级、PCIe 不可纠正错误、非预期掉电、硬盘失效 | 立即，先切业务 |
| 严重 major | 内存 CE 趋势、电压越限、硬盘 SMART 预警、链路/PHY 错误、BMC 看门狗、POST 报错、RAID 卡异常 | 72 小时内闭环 |
| 轻微 minor | 单次 CE、链路抖动、RAID 重建中、SEL 写满、证书/许可、BMC 复位单次 | 纳入周期巡检 |
| 提示 info | 固件升级、系统启动、传感器正常 | 只作时间轴锚点 |

判级三条硬规则：
1. **能导致数据损坏的（UCE/缓存/RAID）不能"观察"，必须计划更换**；
2. **冗余丢失（电源/风扇/内存镜像）必须恢复冗余后才允许做单路维护**；
3. **同一条告警在 7 天内 ≥2 次，或 CE 类数量级上升 → 按劣化处理**，不看单次绝对值。

### 第 3 步：根因关联（单条日志没有意义）
按下面的组合判断，而不是逐条复述：
- 电源输入丢失/整机掉电 + OS 非预期重启 → **供电侧（市电/PDU/UPS）**，不是服务器；
- 风扇失效/转速低 + CPU 降频/过温 → **散热通道**（清灰、满配、进风温度）；
- 硬盘失效/预警 + RAID 降级/重建 → **数据风险最高**，先保数据再换盘；
- PCIe AER + 网卡/存储功能异常 → **插槽/riser/卡**，不是上层业务；
- BMC 复位/看门狗 + 传感器类告警 → **BMC 固件/NVRAM**，会导致散热电源闭环失控；
- POST 报错 + 内存/CPU 级错误 → **上电即失败**，最小化配置复测；
- 系统日志有紧急项但完全没有带外日志 → **证据不全**，先补采再定性。

### 第 4 步：输出结论（三段式）
1. **结论**：健康评分 + 等级 + 一句话（要不要换件、换什么、换前做什么）；
2. **依据**：每条结论配"原始行 + 时间 + 次数 + 定位（DIMM A1 / PSU2 / Fan3 / Disk 5 / BDF）"；
3. **动作**：可执行清单（含厂商命令），并标注谁在什么窗口做。

## 三、定期巡检（让日志有对比价值）

```bash
# 首次：留基线
dsh-hwlog baseline ./logs -o baseline-<sn>-<date>.json
# 下次：只看变化（新增/恶化/已恢复）
dsh-hwlog diff baseline-<sn>-<date>.json ./logs/new
```

关注三件事：**新增**（原来没有的部件问题）、**恶化**（同一告警次数上升，尤其是内存 CE、CRC、PHY）、**已恢复**（确认是修好了还是日志被清空了）。

## 四、工具对应关系

| 目的 | 工具 | CLI |
| --- | --- | --- |
| 分析日志（文件/目录/粘贴文本） | `hwlog_analyze` | `dsh-hwlog analyze` |
| 生成采集清单/脚本 | `hwlog_collect` | `dsh-hwlog collect` |
| 存基线 / 对比 | `hwlog_baseline` / `hwlog_diff` | `dsh-hwlog baseline` / `diff` |
| 看规则库能识别什么 | `hwlog_rules` | `dsh-hwlog rules` |
| 出正式报告文件 | `hwlog_report` | `dsh-hwlog report` |
| 自检插件状态 | `hwlog_doctor` | `dsh-hwlog doctor` |

## 五、常见坑

- **只贴 SEL 结论下"要换主板"**：先核对是否可用最小配置复现，再判主板。
- **把 CE 当故障**：CE 是纠错成功，只有速率上升才是劣化。
- **把"日志被清空"当"问题解决"**：对比报告里的"已恢复"要核对时间点是否与人工操作重合。
- **忽略 BMC 时钟漂移**：不做时间对齐就下因果结论，是硬件误判的第一来源。
- **不带定位就报修**：报修单必须有槽位/编号/BDF（DIMM A1、PSU2、Fan3、Disk 5、0000:65:00.0），否则现场要重新定位。
